# Disposable target runtime qualification

This is an explicit source-only IMP-1/IMP-2 packaging and compatibility slice.
It is not a successor runtime release, general OEP-1 installation, completed
IMP-1/IMP-2, live authorizer, grant activation, or consumer adoption. Kernel 4.2
and identity candidate 5.0 retain their existing meanings. Normal generation
continues to produce the current layout; the target design manifest remains
`design_only_not_selectable`.

Profile inventory v3 adds one closed, qualification-only dependency contract.
The original v2 schema is retained byte-for-byte and the reader accepts its exact
old shape. Unknown and mixed versions refuse. Current generation rules,
packages, profiles, target design and project-path inventories remain unchanged.
The canonical inventory remains the only generation/dependency owner.

Run the explicit disposable route into a nonexistent or empty absolute directory:

```text
python3 -B skills/octon-project-bootstrap/scripts/qualify_disposable_runtime.py \
  --target /absolute/disposable-project --disposable-qualification
python3 -I -B /absolute/disposable-project/octon installation inspect
python3 -I -B /absolute/disposable-project/octon check
```

The canonical minimal/compact generator first renders a validated independent
stage. The versioned `target-path-projection.v1` maps its new implementation and
configuration into `.octon/runtime/scripts`, `.octon/agent`, `.octon/dossier` and
`.octon/agents`. Copied modules retain the existing work, validation and
transaction owners. There is one target state and transaction location, with no
legacy alias or mirrored task store. An explicit compatibility adapter changes
project-root depth and path vocabulary for the copied validator; historical
schema bytes and wire identifiers are unchanged. Dormant package payloads retain
their original content-addressing namespace and remain inactive.

The versioned `.octon/manifest.json` records the actual source revision, copied
source inputs/digests, initial output inventory, canonical inventory digest,
required dependencies and immutable runtime digest bindings. Inspection validates
versions, closed fields, portable confined paths, selected dependencies through
reviewed canonical rules, Python 3.11+, and every required runtime module and copied schema/catalog dependency.
Initial authored-output hashes are provenance, not continuously asserted state.
Derived outputs and the manifest itself explicitly carry null hashes in that
inventory to avoid claiming a self-referential immutable digest; the canonical
derived writer still checks them.
A digest-consistent manifest is not authentication or permission; independent
qualification must bind the checkout and copied assets. A worker able to replace
both entry and verifier remains outside this tested enforcement boundary.

The bounded entry admits inspection, check, doctor, work start/block/handoff/resume
and local transaction apply/recover/rollback. Every work apply alias reaches the
same admission guard. It accepts only the declared work operation classes,
record/focus paths, exact derived writes and exact validation argv. Plans bind
the prior control/verifier bytes through the existing evidence-preimage facility.
Recovery and rollback enforce the same typed record/derived path boundary and
reject forged control/verifier paths and unrelated directory removal. A stale
policy/verifier, forged control write, derived verifier write or changed
validation command refuses. Direct invocation supplies disposable fixture
operation authority; shadow coverage supplies none. These checks do not activate
standing delivery or prove host/provider enforcement.

The focused suite performs an actual task start, existing-task handoff and
receipt-bound rollback, and refuses block without a structured cause. It
interrupts after a durable pending journal and partial write, refuses divergent
unknown local state, reconciles before retry, finalizes an already receipted apply,
and resumes interrupted rollback. IDs, preimages, receipts and recovery journals
remain under their existing owners. Controlled external outcome tests remain
under the existing completion owner, with no actual external provider effect.

The supported predecessor fixture starts at exact Mini 4.2 source revision
`5e2d3025aea6b1574ab984e5ebb89b5602a38535`, uses the existing reviewed 4.2→5.0
identity upgrader, then the qualification API `fixture_conversion_plan` creates
an ordinary exact-digest local transaction. This API requires minimal/compact,
pristine control/verifier bytes, locked delivery, disabled completion, no installed
optional packages, no mixed origin, no target collision, no Git-backed/live consumer, no unknown effect and no pending journal.
It is not exposed as a live consumer upgrader.

The conversion preserves instructions, decisions, tasks, evidence, focus and
project documents byte-for-byte. Every predecessor byte, including source maps,
controls, origins/history and receipts, is retained in `.octon/archive/predecessor`.
The active origin maps only current generated/inventory paths and hashes; its
initial generation and migration history retain their exact meanings and values.
The project-owned artifact registry maps only declared representation paths;
all IDs, owners, facts and non-path fields are preserved. Original bytes remain
in the archive for both transformations.
Only the declared pristine controls receive canonical target path bindings.
Unclassified project files, case-folded reserved collisions and mode drift refuse
before mutation. Mode admission uses exact POSIX bits or the Windows read-only
attribute, matching the host chmod contract; archive/receipt evidence preserves
actual observed modes. This does not qualify ACL or host enforcement. No application content is silently archived away. Every
recognized predecessor inventory row is classified before rendering: supported
authored bytes/typed fields are preserved, declared derived outputs regenerate,
and all other modified, missing or unsafe rows refuse. Custom quality gates and
project-check evidence therefore require separate qualification.
Historical plans and receipts retain their original path meanings and are never
replayed through the target dispatcher. The conversion receipt remains in
`.agent/transactions` as a predecessor recovery capsule, containing no live task
or state owner. The original source transaction owner performs recovery/rollback
of that exact conversion receipt; rollback refuses independently changed
postimages. The suite exercises interrupted conversion and restoration.

Custom Blueprint/kernel 1.0, Plectarium, custom controls, activated grants,
installed packages, external state and mixed inputs remain unsupported. No live
project is converted by this sequence. Broader layout/catalog/profile and consumer
migration work remains in the existing implementation plan.

Proposal regeneration uses the reviewed proposal's existing `created_at` calendar
date as an explicit scaffold rendering input. This deterministic input corrects
the midnight reconstruction limitation without changing historical proposal
schemas, exact proposal binding, target staleness checks or execution-time
freshness/authority. The scaffold rejects malformed dates. The existing accepted
digest still binds the exact candidate bytes, and current apply checks remain.
