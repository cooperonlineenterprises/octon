# Octon Mini 4.2.0 to Octon 5.0.0

This is an explicit project-owned identity migration. Existing snapshots remain
usable and unchanged until their owner reviews and applies an exact plan.
Octon 5.0 is the Mini lineage; the original governed runtime is incompatible.

Use the Octon source/installed bootstrap `octon upgrade plan --target <project>
--authority-source <current project authority reference> --evidence-ref EVD-…
--output <external review file>`. The evidence ID must resolve in the project.
Every non-automatic classification needs a digest-bound review disposition.
Replan with `--proposal` and `--review`, then apply only with the resulting full
`--accept-digest`. The plan/review/evidence never creates permission.

- Preserve project-owned facts, policy, decisions, evidence, stable IDs, initial
  generation and prior migration history. `merge_version_only` changes only the
  reviewed mechanical project version field. Modified/governance paths require
  explicit review; unresolved conflicts do not enter an apply plan.
- Explicitly review removal of the old current `.octon-mini-origin.json` and
  creation of `.octon-origin.json`. The new origin uses `octon.project.origin.v1`
  and product `octon`. Historical Mini schemas and migration entries are unchanged.
  Transaction backup/receipt data retains the exact old origin bytes for recovery.
- A new `octon.project.migration.v1` entry extends the existing MIG ID sequence.
  Its producer is Octon, generator 5.0.0. Old producer identities are not rewritten.
- The kernel compatibility version remains 4.2.0. Existing generic layouts,
  packages and authorization boundaries are retained. Delivery remains dormant
  for new snapshots; migration neither activates nor renews an existing grant.
- Earlier snapshots must use the released Mini tools to reach 4.2.0 first.
  Original-runtime `.octon` installations, mixed origins, unsafe paths, malformed
  provenance, stale plans and an equal/newer installed version refuse mutation.

If interrupted, preserve the pending journal. From the target project's directory,
run `./octon transaction recover --pending .agent/transactions/pending/RCPT-<id>.json`
using the exact pending filename from the interrupted operation. On Windows use
`python -B octon` with the same arguments. Recovery validates the journal's bound
plan digest and preimages/postimages; it has no `--target` or separate digest flag.
The project-local launcher and transaction module remain present throughout this
4.2-to-5.0 transition, including the gap between removing the old origin and writing
the new one. Do not rerun an uncertain apply. For an unchanged completed receipt,
use `./octon transaction rollback --receipt .agent/transactions/receipts/RCPT-<id>.json`.
Recovery refuses intervening edits. No remote effect or automatic replay is part
of this migration. Verify the recovered old snapshot with its bundled tools.
